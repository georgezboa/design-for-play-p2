## 一、美学目标(先定 A,再反推 M)

MDA 的方法是从玩家体验反推机制,不是先堆机制再找说法。这一段序章要产出的主导美学是两个,次要一个:

1. **Discovery(发现)** —— 玩家不是在解谜题,是在破译一台机器的语言。气压、闸瓦、气路的因果关系必须由玩家自己看出来,不是被告知。
2. **Fellowship(伙伴)** —— 单人游戏里的协作感。火车从"被操作的对象"变成"回应你的对象"。
3. 次要:**Expression(表达)** —— 同一个目标允许松、紧两种时间安排,玩家的节奏选择就是他的风格。

**第二段结束时玩家的感受**:我按对了顺序。
**第六段结束时必须变成**:我读懂了它的节奏,我们一起把这件事做完了。

这个差值就是本轮全部设计的唯一验收标准。任何不推进这个差值的机制,不管多聪明,都不加。

## 二、统一机制语法(解决"太乱")

现状"乱"的根因不是美术,是**每一段都发明了自己的一套交互词汇**:第三段排序、第四段限时冲刺、第五段压力带、第六段回声闸门。四段四套心智模型,玩家每进一个房间都要重新学。

四段共享**同一条可以不用文字推断出来的规则**:

> **气压被放掉就会下陷,但它总会回升;门和机械只在你亲手制造的那段下陷里配合你。**

动词表在四段里完全不变,只有四个:

| 动词 | 操作 | 物理含义 |
| ---- | ---- | -------- |
| WALK | 方向键 | 位移,也是唯一的时间成本 |
| BRAKE | E,即时 | 困住气压(隔离风缸,让变化变慢) |
| VENT | E,长按 | 放气,压力下陷 |
| DOOR / LATCH | E,即时 | 只在压力低于阈值时才咬合 |

四段不是四个系统,是**对同一条语法的四次不同追问**:

- 第三段问:**下陷有多久?**(认识这条规则)
- 第四段问:**下陷够你走多远?**(把规则换算成空间)
- 第五段问:**你能把压力停在某个区间吗?**(从阈值到区间)
- 第六段问:**两段下陷能对齐吗?**(从一个自己到两个)

## 三、难度阶梯:每段只加一个新变量

| 段 | 新变量 | 玩家真正的决定 | 失败如何从机械上读出 | 恢复 |
| -- | ------ | -------------- | -------------------- | ---- |
| III | 恢复时间(~3s) | 放气和开门之间空多久 | 针爬回刻度上方,门闩抬起一掌高又落回,一声闷响 | 再放一次气,门闩即时复位 |
| IV | 距离 | 什么时候离开阀门 | 闸瓦松开、针越过刻度、拖车闩弹回 | 走回阀门重放,进度不丢 |
| V | 区间(不再是阈值) | 如何用 BRAKE 压住回升速度,把针停在带内 | 灯灭、轮组停转、针滑出带外 | 松手,压力自行回满,原地重试 |
| VI | 第二段延迟的下陷 | 什么时候放本地阀,让回声的下陷和你走到门口重合 | 回声到达时压力已回升,门不动,回声散成一团蒸汽 | 回到本地阀重新录,旧回声清除 |

**现有机制的处置**(必须明确,否则实现会两套逻辑并存):

- 第四段那个**看不见的 3500ms 倒计时(`manualWindowMs`)删除**。它是当前设计最大的隐性缺陷——玩家不知道自己在被计时。计时器换成气压表:窗口从一个隐藏变量变成一个玩家看得见的物理量。这是本轮最重要的单点修正。
- 第五段的**压力物理模型保留**(`bleedPerSec` 等五个速率沿用),但**金色高亮删除**。审计已证实那个高亮让"读机器"完全没必要,直接废掉了这一段的设计意图。
- 第六段的**三道回声闸门(轮组/气路/车钩)保留,不采纳 DeepSeek 的删除建议**。理由见第四节。

## 四、方案取舍:我不采纳 DeepSeek 的第六段

DeepSeek 提议把第六段重做成"延迟 4 秒的远端阀门同步",删掉现有三道闸门。**驳回,理由有三个,前两个是硬约束:**

1. **算术上几乎不可能成立。** 第六段可用跨度 x4000–4778 = 778px,走完全程 3.89s,而它要求 4s 延迟——只剩 **0.11 秒**余量,且必须阀门恰在 4000、门恰在 4778。任何布局微调都会让这一段变成不可通关。
2. **它违反了已锁定的失败规则。** 现有第六段刻意设计成"PAST 在闸门前无限等待,没有失败状态,张力来自理解而不是反应"。DeepSeek 明确要"移除无限等待,建立真实后果",这是把一个理解型关卡改成反应型关卡,和"失败必须局部、可快速恢复"以及整段的美学目标(Fellowship 而非 Challenge)直接冲突。
3. **它是四段里唯一的大规模新建。** Kimi 的台账判定它需要输入录制、确定性重放演员、第二个压力域、亚秒级同步窗口,全都不存在,成本 large、风险最高。

现有的三道闸门反而**已经是 Fellowship 的最佳表达**:BRAKE 的含义从"停车"变成"给同伴搭一座桥"。这正是第一节要的那个差值。所以第六段**只做一件事**:把它接入统一语法(闸门的清除条件用压力状态表达,而不是命令名),不重做。

## 五、算术审计:三处必须修正的数字

我用真实速率独立验算了双方的数字。**DeepSeek 的第五段规格在数学上不可能实现:**

| 状态 | 针的斜率 | 穿过 20 单位带宽耗时 |
| ---- | -------- | -------------------- |
| 放气,未刹 | −30/s | 0.67s |
| 放气,已刹 | −21/s | 0.95s |
| 回升,未刹 | +30/s | 0.67s |
| **回升,已刹** | **+9/s** | **2.22s** |

最慢的漂移是"已刹回升"的 2.22s,而 DeepSeek 要求**连续保持 2.5s**——针必然在达标前滑出带外。**这一段按其规格实现必然做不出来。**

修正:带宽从 20 放宽到 **30(35–65)**,已刹回升可保持 3.33s,对 2.5s 要求留 0.83s 余量。或者把保持时长降到 2.0s。**我选放宽带宽**,因为缩短保持时长会削弱"停住"这个动作的体感。

另两处:

- 第三段"~3000ms 恢复"**缺少前提**。按未刹回升 30/s,从 0 回到阈值 30 只要 1.0s,不是 3s;只有"已刹回升 9/s"才接近 3.33s。实现前必须明确恢复用哪个速率,否则这个数字是空的。
- 第四段 600px = 3.00s 正确,几何也塞得进 x2400–3178(闩位 3177,阀位 2577)。但这让阀门贴着 2577、闩贴着守卫线,**第三个交互物就再也放不进 96px 间隔**。采纳 Kimi 的建议:**先用 560px(2.80s)**,留出布局余量和 0.2s 宽容度。

## 六、UI 与操作教条

玩家要感知四类信息。原则:**能用机械表达的绝不用 HUD。**

| 信息 | 表达方式 |
| ---- | -------- |
| 数量(压力) | 齐眼高的黄铜压力表,连续读数。**带边缘必须有刻度线**——纯指针在 960×600 暗色调下读不准区间(Kimi 判定,我同意) |
| 期限(窗口) | 门闩本身是一只随压力回升而缓慢合拢的爪。窗口是一个看得见的物理闸门,不是隐藏计时器 |
| 因果(X 必先于 Y) | 一条可追溯的黄铜气路横贯窗带下方,压力沿管travelling可见。管在下陷时明显松垂 |
| 成败 | 机械先反应,然后才是门。绝不用文字或仪表单独宣布 |

必须删除的:

1. 第五段的**金色下一步高亮**——它废掉了整段的设计意图。
2. **所有悬浮倒计时**。
3. 任何**说出正确答案的错误提示**。

保留的唯一 HUD 让步:段落编号铭牌(黄铜搪瓷,车厢常识物件)。

控制器按**安装面**分离,不再是一排等宽按钮:BRAKE 地面铸铁支架、VENT 墙面黄铜轮、DOOR 车厢边缘门闩。高度和轮廓都不同,玩家凭形状就能区分。

## 七、音频:当前系统做不到方案要求的声音

这是一个必须点明的硬缺口。`src/sfx.js` 只有**一个振荡器 + 一个增益**,波形限于 square/triangle/sawtooth,**没有噪声源、没有滤波器、没有混响**。

方案里的"气动嘶声""气路松垂""门闩落位闷响""接近低语"**全部需要噪声源加滤波**,当前一个都做不出来。而且 17 个音效**零音高随机**,重复触发完全一样。

最小改动:在 `sfx.js` 里加一个生成式白噪声 `AudioBuffer` + 一个 `BiquadFilter` + 每次调用 ±5–8% 随机失谐。这是**整个呈现层性价比最高的一处改动**,也是本轮唯一必须动的非视觉系统。

## 八、实现顺序与试点

**第四段作为试点先建。** 理由:成本最低(Kimi 判定 small),复用现有压力模型和交互拾取,只引入一个新变量(距离),并且它能在不牵扯回声同步的前提下,干净地验证"压力表 + 门闩爪"这套新语法到底能不能被非玩家读懂。

顺序:**IV(试点)→ III(接入语法)→ V(放宽带宽后)→ VI(仅接语法,不重做)**。

第四段试点 QA 路线:

1. 起始:玩家 x=2400,压力 100,拖车闩锁定。
2. 长按 E 放气,同时向右走。约 2.33s 时压力落到阈值,松开 E。
3. 走到 x≈2977(560px 处)按 E,闩应开启,机械先动,再触发完成运镜。
4. 失败验证:提前松开 E,让压力在到达前回升。`render_game_to_text()` 必须显示按 E 时 `pressure >= threshold` 且闩保持锁定;玩家走回阀门重试,**整段不重置**。
5. 若这条路线走不通,560px 距离或无 HUD 指针其一已经失败,**不得开始第六段**。
