# Phase 1 补全优化计划

制定日期:2026-07-28
Phase 1 定义:对应美术工作簿的 **M1 垂直切片**——让「序章 + 第一章」两节车厢
看起来像最终游戏、无文字也能读懂机制、可以直接课堂试玩。
对应 Obsidian 笔记推荐实施顺序的第 1–3 步(资产管线 → 可复用世界场景 →
一节完整教学车厢),其中第 1 步已完成。

## 一、现状盘点

### 已完成(不要重做)

- 世界背景资产管线:10 张全景 → 30 块 4096px 纹理,`assets:check` 构建门禁,
  `?world=N` 预览,产物约 19 MiB。
- 4,800px 六段式序章:DOOR/BRAKE/POWER/VENT/COUPLE 时刻表教学、实体转向架
  操作、录制回声同步、完成运镜语法、`SERVICE SET` 持久房间、时代感机械动效、
  发车过场和 `CHAPTER ONE // THE SAFETY TEST` 章节卡。
- 全部序章 QA 路线、production build、浏览器回归均通过(2026-07-28)。
- 美术生产清单工作簿(179 个资产包,M0–M4 里程碑)。

## 二、工作流拆分

### 工作流 A(产品,最高优先):第一章决策 → READY 任务

1. **A1 决策第一章核心交互。** 必须满足 `NEXT_TASK.md` 的五条约束:表达
   AI 末世里的"安全测试"、以火车/机器/NPC/环境为伙伴、教一条规则再扭转、
   不重复时刻表排序、以车厢或车外的可见变化收尾。候选方向(建议取其一):
   - **候选 1(推荐)— 「考官反转」:** AI 检查系统对*玩家*执行安全测试。
     序章里玩家指挥火车;第一章里车载检查程序发出指令,玩家用序章学会的
     物理器件语言*应答*。扭转:某条指令会伤害火车,玩家必须违抗,火车用
     物理动作掩护玩家。伙伴关系从"玩家指挥火车"翻转成"火车掩护玩家",
     直接复用已有器件交互语言,又不重复"排序解谜"。
   - **候选 2 — 「传感诊断」:** 车厢传感器被末世 AI 污染,仪表读数与
     底层机械真实状态矛盾;玩家学会"相信机械、不相信屏幕",通过观察
     真实的轮组/气路裁决每一次安全检查。
   - **候选 3 — 「静默通过」:** 外部 AI 扫描列车,玩家需在扫描节奏间隙
     操作器件,把火车伪装成无人驾驶的死车;节奏窗口机制与序章回声同步
     形成呼应但交互类型不同。
2. **A2 写 READY 任务。** 用 `NEXT_TASK.md` 模板填玩家结果、范围内/外、
   四步交互序列(教 → 用 → 扭 → 果)、验收标准(含 `render_game_to_text`
   状态)和精确 QA 路线,状态改 `READY`。第一片只做"教 + 用"一小段,
   不做整节车厢。
3. **A3 验收循环。** Codex 实现后按验收标准过一遍,`ACCEPTED` 或写具体
   修订意见,同步 `PRODUCT_STATE.md`。

### 工作流 B(技术,与 A1/A2 并行):共享基件与数据驱动

1. **B1 拆共享车厢美术基件。** 把序章的车壳、车窗、隔断、气动门序列、
   `SERVICE SET` 静置态、完成运镜语法从 `tutorialTrainRoomsArt.js` /
   `TimetablePuzzle.js` 中抽成共享模块,参数化材质族(第一章换 AI 末世
   材质语言)。验收:用共享包 + 末世材质在一天内搭出第一章灰盒外壳。
2. **B2 每车数据清单。** 车厢身份(世界、材质族、全景、机制类型)与
   序列顺序分离存储(笔记明确要求车序仍可能调整);第一章作为第一个
   数据驱动车厢加载,不再新增一个单体场景分支。
3. **B3 最小持久化。** 章节进入点 + 已完成分段的存档/读档,刷新后能从
   第一章开头继续,不用重打序章。范围刻意压小:localStorage 即可,
   不做菜单系统。

### 工作流 C(打磨与卫生,穿插进行)

1. **C1 序章试玩修正。** 针对 `progress.md` 遗留问题做一轮定向试玩:
   同步保持窗口宽容度、失败重试节奏、首分钟无文字可读性;只修确认的
   问题,不重设计。
2. **C2 角色定稿。** 推动团队锁定主角/列车长最终方向,替换临时剪影
   (M1 明确交付项;若团队未定,保留剪影并在工作簿标记 `暂缓`,不阻塞)。
3. **C3 工程卫生。** 解决 GitHub 推送认证,把本地未提交的序章工作切成
   有意义的提交推上远端;加 CI(`npm ci` + `assets:check` + `build`,
   progress.md 已列为 TODO)。这是当前最大的单点风险——全部序章成果
   只存在于一台机器的未提交工作区。

## 三、执行顺序与依赖

```
第 1 步(立刻,可并行):
  A1 决策第一章交互          C3 提交/推送现有成果
第 2 步:
  A2 写 READY 任务           B1 拆共享基件(A1 决策后按其机制需求收口)
第 3 步:
  Codex 实现第一章第一片(用 B1 基件 + B2 数据清单)
第 4 步:
  A3 验收 → C1 序章定向修正 → B3 持久化 → C2 角色(视团队进度)
```

C3 放在第 1 步是刻意的:先保住已有成果,再生产新内容。

## 四、Phase 1 完成标准(M1 出口)

- 序章 → 章节卡 → 第一章第一片全程可玩,无继承战斗原型出现在主路径上。
- 第一章截图"不再像全屏背景 + 占位几何";其机制无文字也能读懂
  (工作簿 M1 退出标准原文)。
- 两节车厢各有一个可截图的机制时刻。
- 共享车厢基件被两节车厢同时使用,第三节车厢可在一天内灰盒成型。
- 刷新页面可从第一章继续。
- 远端 `main` 包含全部工作,CI 对 `assets:check` + `build` 亮绿。
- 序章遗留的三个试玩问题各有一个"已修/已确认不修"的结论记录。

## 五、明确不做(Phase 1 范围外)

- 第 3–10 节车厢内容、三结局、列车长 Boss、菜单系统、库存/食物机制。
- 重写继承战斗原型(保留为素材,不删除、不整合)。
- 换角色美术风格方向(只做"锁定并替换",不做探索)。
