## 一、"乱"的量化证据(取自真实代码,非推测)

| 文件 | PAL 引用 | 写死颜色 |
| ---- | -------- | -------- |
| `src/textures.js` | 29 | 85 |
| `src/scenes/GameScene.js` | 5 | 67 |
| `src/art/tutorialCarArt.js` | **0** | 28 |
| `src/art/tutorialTrainRoomsArt.js` | **0** | 85 |
| `src/tutorial/TimetablePuzzle.js` | **0** | 124 |

**全项目 196 个独立颜色值,其中约 150 个只用了一次。**

关键发现:`src/palette.js` **本来就存在**,而且写着明确的设计规则——"整个场景是一条单调的明度阶梯,离相机越近越暗:背景 > 远景层 > 近景层 > 前景;任何一处打破单调性,深度感就会塌掉"。但**三个车厢美术文件对它零引用**。也就是说,规则被写下来了,然后被 73% 的颜色字面量无视。车厢内部不只是用了无关的颜色,它用的是**另一套明度结构**,直接违反已锁定的"内部继承外部材质语言"规则。

近似重复已验算确认(最大通道差 / L\* 差):

- `0x687981` vs `0x697980` —— 差 1 / **0.04 L\***,两个字面量,肉眼完全无法分辨。
- `0x26343b` / `0x263238` / `0x26363d` —— 互差 ≤5 / **≤1.57 L\***,三个字面量,一个颜色。
- 黄铜族 14 个、深蓝灰族 12 个、中灰蓝族 10 个,均属同类冗余。

深度层级同样是意外而非设计:30 次 `setDepth` 里有 **20 次挤在 53–61 这九个相邻整数**里。这不是分层,是"按写代码的顺序随手给数字"。任何一次重排都会静默改变遮挡关系。

**结论:第一优先修颜色,不是修构图。** 构图上的杂乱(六个等宽按钮像 HUD)是明度结构失效的**结果**,不是独立病因——那六个按钮用的是全饱和界面色,明度结构里没有任何东西把它们降级。

## 三、明度阶梯与主角规则(**已修正外部模型的错误**)

各平面目标 L\* 区间:

| 平面 | L\* |
| ---- | --- |
| 车窗外全景(透过玻璃) | 18–32 |
| 车窗框 | 12–20 |
| 车厢壳/搪瓷内衬 | 14–28 |
| 机械中景(车底、未激活房间) | 10–22 |
| 交互控件面 | 24–40 |
| **主角** | **50–65** |
| 前景遮挡物 | 4–10 |

**必须修正的一处**:Kimi 主张"主角靠与最亮控件面之间 20 点 L\* 的差距胜出,而非靠发光"。**这个数字是错的。**验算显示 `HERO_BASE` L\*=91.3,而它自己划入控件面的 `BRASS_HI` L\*=85.8,**实际差距只有 5.6 点,不是 20 点**。按其原规格实现,主角在黄铜高光旁边根本不会突出。

修正规则(三条,可断言):

1. 主角以 `HERO_BASE` 烘焙,并且**禁止对主角染色**(代码断言:主角所在深度带 tint 必须为 `0xffffff`)。
2. `BRASS_HI`(L\*=85.8)**不得用于大面积控件面**,只允许用于 ≤2px 的棱边高光。控件面本体上限为 `BRASS_MID`(L\*=70.1),这样与主角的真实差距是 **21.2 点**,才符合原意图。
3. 状态灯可以在**饱和度**上冲高,但**面积**受限:单个不超过 6×6 px。

因为 tint 只能变暗,所以主角靠的是这 21 点差距加上运动,不靠 bloom——这与"不使用发光后处理、钨丝光读作金属上的反射"的锁定方向一致。

**廉价的合规检查**(一个工程师半天能做完):所有烘焙期的 `fillStyle`/`strokeStyle` 走一个 `C(color)` 包装器,若颜色不在命名表内就**抛异常**。评审时把每段的截图转灰度并缩到 32×20——主角必须是最亮的一块,状态灯第二,其余全部更暗。主角不突出,就是阶梯坏了。

## 四、深度架构:8 个命名带,间隔 100

| 带 | 深度 | 内容 |
| -- | ---- | ---- |
| EXTERIOR | 0 | 全景切片 |
| WINDOW | 100 | 玻璃染色、窗框 |
| SHELL | 200 | 墙体、座椅、未激活房间 |
| MACHINERY | 300 | 车底(世界 y 600–886)、转向架、风缸 |
| SET | 400 | SERVICE SET 完成态机械 |
| ACTORS | 500 | 主角、NPC |
| CONTROL | 600 | 交互控件、仪表、灯 |
| FOREGROUND | 700 | 暗角、前景剪影 |
| CURTAIN | 800 | 仅段落转场遮罩 |

间隔 100 是为了让随手写的整数永远不可能撞车。

两处已知隐患的处置:

1. **深度 70 的全屏静态暗角**:它现在压在所有世界物体之上,而且恰好糊住最需要清晰的那些像素。把边角压暗**烘焙进 SHELL 纹理**(一次性烘焙成本),只在 700 保留不超过 10% 的上下边缘。它绝不可位于 CONTROL 之上。
2. **深度 45、`scrollFactor(0)` 的前景条**:它固定遮住屏幕第 526–600 行(整帧的 12%),并静默隐藏所有 depth ≤44 的内容。移到 700,收窄到 560–600 行,并从纯色 `0x05070b` 改成 2–3px 阶梯状 `VOID` 剪影(带铆钉/吊环形状),让它读作近处座椅靠背而不是黑色信箱条。**第 526–600 行内永远不得放置任何与玩法相关的东西**,控件布放时断言这一条。

SERVICE SET 完成态置于 SET(400):在演员之下、壳体之上,用固定的 `VOID_LIFT` 40% alpha 压暗,**永不重排**。未激活房间置于 SHELL 带,同样压暗,激活前其上不得有任何 400 以上的物体。

## 五、构图与清晰度规则(可测试,非愿望)

1. **安装面规则**:每个控件必须画成附着在母表面上(面板/支架/壳体),母件在各边都比控件大至少 4px。悬空按钮即 bug。
2. **同段内不得有两个控件共享相同轮廓 + 颜色**。用形状(手柄/仪表/钳/灯)和尺寸区分,功能从形态读出。
3. **屏幕预算**:交互控件占 960×600 画面不超过 **25%**;主角精灵高度 ≥48px,且**永不小于最大的控件**。这条直接针对"主角比界面还小"。
4. **窗带规则**:窗口开口所在行内不得放置任何 UI、文字或状态灯;窗里只有全景和反射。信息一律位于窗台线以下。
5. **无数字仪表可读性**:表盘直径 ≥28px,`VOID` 表面,`BRASS_HI` 指针宽 ≥2px,3–5 条 `SKY_RIM` 刻度,指针用机械式步进动画(符合时代动效词汇),红区为单段 `LAMP_ALERT` 弧。靠**指针角度**读数,不靠数字。
6. **黑色预算**:纯 `VOID` 每段不超过画面 **30%**,且必须聚集在车底和前景遮挡物,**绝不出现在演员带**。
7. **噪点删除**:把截图缩到 480×300,任何消失的细节都是噪点——**删掉它,而不是给它换个颜色**。那约 150 个单次使用的字面量大部分属于此类。
8. **每段仅一个焦点**:同一时刻只允许一个 `LAMP_ALERT` 和一个钨丝光源处于激活状态。
